## 一、测试目标

本项目的核心风险不是"功能缺失"，而是**长时间运行/异常路径下的崩溃与错播**：

| 风险 | 历史表现 | 本次测试的应对 |
|---|---|---|
| FD 耗尽 → SIGABRT | 真机连续播放 5.5h 后 `Looper::rebuildEpollLocked` 断言崩溃 | 代理端到端用例 + **负向验证**证明能拦截该回归 |
| 去广告误删正片 | 《给阿嬷的情书》实测报"跳十几分钟" | HLS 去广告三套用例（含真实样本）成对固化 |
| 续播/拖动跳变 | 确认弹回、重试拽走、进度条与画面不同步 | 详情页播放核心/续播/进度用例 |
| 资源无界增长 | 代理会话运行期从不淘汰 | LRU 淘汰用例 + 端到端计数断言 |

**测试目标**：把"靠真机长时间等待才能发现"的缺陷，前移为"CI/本地秒级可复现"的自动化用例。

---

## 二、测试分层模型

按**可测性**与**价值**分五层，逐层向上成本递增：

```
L4 真机/人工验证   崩溃复现、播放观感、硬件解码兼容     ← 不可自动化，但不可省略
      ▲
L3 端到端集成测试  真实 HttpServer 假源站 + 真实服务   ← 本轮新增（代理链路）
      ▲
L2 组件/页面测试   Widget 测试、布局与手势纯函数
      ▲
L1 服务/状态测试   Provider 状态机、Service 逻辑（mock 隔离平台通道）
      ▲
L0 纯逻辑单元测试  无 IO、无平台依赖的判定函数          ← 数量最多、最稳、最快
```

### 各层的技术约束（重要）

| 约束 | 原因 | 应对 |
|---|---|---|
| `flutter test` **发不出外网请求** | 测试沙箱无网络 | 判定逻辑抽成纯函数测；端到端用**本地回环**假源站 |
| `flutter test` 默认**拦截全部 HttpClient**（返回 400） | `TestWidgetsFlutterBinding` 会装 `_MockHttpOverrides`（防测试意外打网络） | 需要真实回环的用例：`ensureInitialized()` 后 `HttpOverrides.global = null` + mock 掉 `path_provider` 方法通道（见 6.5） |
| `flutter test` **跑不了真实播放器** | media_kit/libmpv 需原生库 | 播放器相关判定抽成纯函数；播放本体留 L4 |
| 平台通道（`path_provider`/`hive`/`screen_brightness`）在单测中不可用 | 无真实平台 | mock 方法通道 / 注入平台实现；只测不依赖平台的分支 |
| `/proc/self/fd` 在 Windows 测试宿主不存在 | 平台差异 | FD 判定抽成纯函数，注入 fd 值测边界 |
| 沙箱代理会劫持 `flutter_tester` 的 WebSocket | 环境变量 | **跑测试前必须清代理**（见第六节） |
| **C 盘写满 → `ENOSPC`** | 磁盘满会让 `flutter test` / `flutter build` / 甚至 shell 自身全部失败 | 跑构建前先确认 C 盘余量 ≥ 5GB（见 6.4） |

### 4.2 第二轮：资源释放与硬件解码（45 条，v1.0.40）

#### 4.2.1 关键设计：为什么播放器事件要「多播」

原设计里 `PlayerService` 对外是**单值回调**（`onPositionChanged = ...`），
`PlayerProvider` 则绕过服务、直接订阅 `player.stream.position`。

后果：播放器实例一旦被回收重建（fd 兜底 / 硬解降级），`PlayerProvider` 的
订阅仍挂在**已 dispose 的旧 Player** 上 → 进度、时长、缓冲**永久冻结**，
而 `PlayerProvider` 完全不知道自己已失效。

修复：外部一律订阅**服务**的事件通道（`PlayerEventChannel`，多播），
通道在播放器重建时**不重建**，订阅者无感。

对应回归用例：`player_listeners_test.dart` 的
「回收重建场景（真实缺陷回归）」两条。

#### 4.2.2 关键设计：硬解为什么要「探测 + 回退」而不是「关掉」

原实现只有一个布尔开关，关闭写 `hwdec=no`，开启写 `hwdec=auto-safe`：

- **默认关闭** = 让所有用户用 CPU 软解 1080p/4K（省电与流畅度全丢）；
- `auto-safe` 是黑盒，App 侧不知道实际用上了哪个后端、是否真在硬解。

修复（`hw_decode_policy.dart` + `PlayerService`）：

1. **分档**：`mediacodec`（零拷贝）→ `mediacodec-copy`（拷贝式）→ 关闭；
   Android 默认走**拷贝式**（硬解照开，只是避开零拷贝的互操作坑）；
2. **运行时探测**：mpv 官方属性 `hwdec-current` 返回**当前实际生效**的后端
   （`no` = 软解；属性不可用 = 尚未起播）。起播 3s 后读一次就知道硬解有没有用上；
3. **逐级回退**：连续探测到软解 → 自动降一档并**持久化**，下次启动不再重踩；
4. **崩溃归因**：原生崩溃处理器在写栈时附带 `hwdec-state:` 快照（当前档位），
   App 启动时扫描崩溃文件，**自动**识别硬解相关崩溃；累计到阈值再降一档。

> 用户显式关闭时，策略**不做任何自动干预**（不越权替用户做主）——
> 见 `hw_decode_policy_test.dart`「用户显式关闭：不动它」。

### 4.1 第一轮：FD 泄漏兜底与 LRU 淘汰（37 条，v1.0.37–v1.0.39）

> ⚠️ 本节描述的 FD 兜底回收机制已于 2026-10-22 **整体删除**（相关源文件与测试文件一并移除）。

针对 FD exhaustion 崩溃的**触发判定**与**代理资源淘汰**。两类判定逻辑原本都内联在服务类里（依赖 `Player` 实例 / 依赖服务状态），无法单测；本轮各抽为一个纯函数，成为单一事实来源：

- `evaluateRecyclePolicy()`（`lib/services/player_recycle_policy.dart`）——回收触发判定；
- `evictOldest()`（`lib/services/proxy_eviction.dart`）——代理/LRU 淘汰。

| 文件 | 条数 | 覆盖 |
|---|---|---|
| `test/services/proxy_eviction_test.dart` | 10 | 空/未超/恰好等于上限不淘汰、超出部分精确淘汰、`maxCount=0` 与负值、被淘汰的是**最旧（插入序）**、剩余保持插入顺序、返回条目携带原 value 供调用方关闭资源 |
| `test/services/local_media_http_server_e2e_test.dart` | 14 ★ | **用真实 `HttpServer` 假源站 + 真实 `LocalMediaHttpServer` 走完整链路**（源站 m3u8 → 解析器 → 代理会话 → 拉分片） |

★ e2e 分组：正常路径（索引/分片 200、内容一致、回环地址）、**fd 泄漏回归**（源站 403/404 → 透传且响应体被完整 drain）、健壮性（未知 token/序号越界/HEAD）、LRU 上限（12 个会话 → ≤8）、远程媒体代理透传。

#### 判别手法（为什么这个测试能真的抓到 fd 泄漏）

源站在错误响应里写 **4MB body**（远超 socket 缓冲）：

- 代理**正确 drain** → 源站的 4MB 全部写出 → 记录 `true`；
- 代理**漏 drain** → 源站写入阻塞/报 BrokenPipe → 记录 `false` → 用例失败。

> ⚠️ 夹具设计要点：错误分片必须放在**序号 5**（预取窗口 `prefetchAhead(-1)` 只覆盖 0..3）。若放在窗口内，会被"下载路径"抢先取走——那条路径也做了 drain，会**掩盖**流式路径 `_tryStreamHlsSegment` 的 drain 缺失，导致负向验证失真（第一版夹具就踩了这个坑，负向验证时测试仍然通过）。

### 4.3 第三轮：单例存亡、多源合并与 dispose 幂等（29 条，v1.0.41）

这一轮全部源自**全局静态审计**发现的存量缺陷，其中第一个是 v1.0.40 自己引入的 showstopper。

#### 4.3.1 `api_service_multi_source_stream_test.dart`（5 条）——多源并发流式合并

修复两个缺陷：

1. **只合并前 4 个源**（正确性 bug）：`_searchSourcesConcurrently` 的滑动窗口里，`_mergeStreams` 装配时拿的是 controller 列表**一次性快照**，第 5..N 个源（窗口滑动后加入）永远拿不到 listener，且关闭条件是"初始 4 个完成"→ 启用源 >4 时提前收摊，UI 表现为多源搜索只搜前 4 个源；
2. **N 个订阅无取消路径**（泄漏）：改为单一事件队列直接合并（不建 per-source controller），消费者取消即停。

覆盖：6 个假源站 >并发上限时全部 yield、乱序返回不丢不重、completed 单调、消费者取消后不抛未捕获异常、单源搜索不污染 `_currentSource`。

> 测试环境坑：`TestWidgetsFlutterBinding.ensureInitialized()` 会安装 `_MockHttpOverrides`，把**所有** HttpClient 请求 mock 成 400 —— 需要真实 loopback 的用例必须先 `HttpOverrides.global = null`；`path_provider` 走方法通道，也要 mock。

#### 4.3.2 `dlna_service_test.dart`（6 条）——搜索定时器泄漏与挂死

`Timer(timeout, …)` 返回值被丢弃（无句柄）：面板每开合一次漏一个最长 12s 的定时器 + service 引用链；`finally` 同步复位 `_isSearching` 使 12s 内重入守卫失效；`stopSearch()` 杀订阅后旧 caller 的 future **只有那个定时器能完成** → 永久挂起。

修复：`_searchTimeoutTimer` / `_searchCompleter` 字段化，stopSearch 取消定时器并**完成挂起的 completer**；重入返回快照（不再返回内部可变列表本体）。

覆盖：超时后正常返回、stopSearch 后旧 caller 立即拿到快照不挂死、旧定时器不产生陈旧完成、重入立即返回、取消后二次搜索不受旧定时器搅乱。

#### 4.3.3 `player_service_test.dart` 新增（3 条）——单例存亡契约

**v1.0.40 引入的 showstopper**：`detail_player._releasePlayerResources()` 对**单例**调了 `playerService.dispose()` → `_disposed = true` 永久生效 → 关掉第一个详情页后播放器单例即死亡，再打开任何视频都没反应（且已随 v1.0.40 包发布）。

修复：新增实例级释放 `releasePlayerInstance()`（新 ResourceScope + 置空 Player/VideoController，**不碰 `_disposed`、不清事件通道**），详情页改调它；单例生死只归应用退出路径。

覆盖：`releasePlayerInstance` 后 `isDisposed=false` 且实例置空；真 `dispose` 后 `releasePlayerInstance` **不能**复活服务；详情页关闭路径组合不炸。

#### 4.3.4 `singleton_dispose_idempotent_test.dart`（5 条）——单例 dispose 幂等

接入应用退出路径（`_MovieAppState.dispose` 统一释放 4 个单例）后暴露的新回归：**单例跨测试共享**，widget 测试反复装配-卸载 `MovieApp` 让同一单例被 dispose 多次 —— ChangeNotifier 重复 dispose 后再 `notifyListeners` 直接抛 `debugAssertNotDisposed`（`TorrentPlayerService.dispose → stop → _setState` 路径，曾致 `home_page_test` / `detail_page_test` / `player_page_test` 三个文件 7 条用例红）。

修复：4 个单例（Torrent IO/Web 双实现、Dlna、DeepLink、LocalMediaHttpServer）统一加 `_released` 幂等守卫；Torrent 的 `_setState` 同样挡已释放状态。

覆盖：每个单例连续 dispose 不抛不挂死；dispose 后 stop 不抛。

> 负向验证：摘掉 Torrent 守卫 → 本文件 2 条红 + 三个 pages 文件复现 7 条红。

## 五、回归测试的负向验证（方法论）

**规则：新增回归用例必须证明"把修复摘掉，它会失败"。** 否则用例只是"陪跑"，无法防回归。

本轮实证记录：

| 步骤 | 操作 | 结果 |
|---|---|---|
| ① 基线 | drain 修复在位 | 14/14 通过 |
| ② 负向 | 临时摘除 `_tryStreamHlsSegment` 的 `await r.drain()` | ❌ 失败：`Expected: non-empty, Actual: []`（源站 body 永远没被读完）→ **用例有牙齿** |
| ③ 还原 | 恢复修复 | ✅ 14/14 通过 |

同样的方法适用于任何"防回归"用例：改动生产代码 → 跑用例 → 确认它真的红了 → 还原 → 确认它真的绿了。

### 7.1 顺带修掉的存量缺陷：陈旧断言

全量跑批时抓到 `playback_strategy_test.dart` 一条**存量失败**（非本轮引入）：

```
Expected: <100663296>   ← 测试硬编码 96MB
Actual:   <25165824>    ← 代码实际 24MB
```

排查结论：`lib/services/playback_strategy.dart` 存在**未提交改动**——`balanced`
（默认档）的 demuxer 读缓存从 96MB 调到了 24MB（应为降低内存占用、规避 LMK），
但测试仍写死旧数值，属于**陈旧断言**。

修复方式**不是**把 24MB 抄进测试，而是把断言从「硬编码数值」改为「契约」：

```dart
expect(cfg.demuxerBufferBytes, balanced.demuxerBufferBytes);  // 未知键 ≡ balanced
expect(cfg.demuxerMaxBytes,  greaterThanOrEqualTo(cfg.demuxerBufferBytes));
```

这样下次再调参，用例不会再次变成陈旧断言而误报失败。同时补充了「档位齐全且
字段合法」用例（各档位字段自洽性 + `demuxerMaxBytes ≥ demuxerBufferBytes`）。

> **经验**：断言具体数值会把用例绑死在实现细节上。凡是「实现允许调整」的参数，
> 应断言**关系/契约**而非**绝对值**；绝对值只用在真正不可变的不变式上。

## 九、交付流程的一个坑（务必留意）

`tool/package_deliverables.py` **只压缩现有的 `build/` 目录，不会重新构建**。

实测：改完代码直接跑打包脚本，产出的 `罐子_web_v1.0.40.zip` 与
`罐子_windows_v1.0.40.zip` 里装的是 **10-19 的旧产物**（`build/web/main.dart.js`
时间戳为 10-19 19:40），但文件名却标着 v1.0.40 —— **版本号与实际内容不符**，
比没有交付物更危险。

正确顺序：

```bash
# 1) Android（脚本用的就是这个现产物，没问题）
flutter build apk --release --split-per-abi

# 2) Web（先清增量残留，否则 build/web/assets 会留下陈旧文件）
rm -rf build/web/assets
flutter build web --release --no-wasm-dry-run

# 3) Windows
python tool/ninja_build.py build

# 4) 最后才打包
python tool/package_deliverables.py
```

> 打包后务必核对：APK 用 `aapt2 dump badging` 看 `versionName/versionCode`；
> Web/Windows 用**产物文件时间戳**确认是本次构建（脚本不会替你验证）。
