## 0. 一句话结论

> **「磁力结果时有时无、波动巨大」的根因不是超时没调好，而是只有 1 个能出结果的源（Torrentio）。**
> 任何单源架构都必然抖动。第一优先级是引入**独立生态的第二个源**，而不是继续调超时。
> 实测找到可用解：**Knaben 聚合 API**（手机 200/3.6s，支持中文原名直查，一次返 100 条，带实时做种数）。

## 1. 别人怎么做的（源码级）

### 1.1 magnet-cli（Rust，最值得抄的一个）

源码结构（README 明确列出）：

```
src/
├── main.rs        # 命令执行、输出、过滤、排序
├── search.rs      # 并发调度、错误汇总、去重
├── model.rs       # Torrent 模型、hash/magnet 归一化、matches_query
├── cache.rs       # 原子快照读写
└── providers/
    ├── mod.rs     # Provider trait + HTTP wrapper
    ├── knaben.rs  ├── apibay.rs  ├── bitsearch.rs
    ├── btgoogle.rs├── animegarden.rs
    └── feeds.rs   # Nyaa/Sukebei/Torznab/RSS/DMHY/Mikan 共用一套
```

关键设计：

| 设计点 | 它的做法 | 对我们的意义 |
|---|---|---|
| 抽象 | `Provider` trait，一个源=一个模块；RSS 类 6 个站共用一个 `feeds.rs` | 我们每加一个源要改 4 处（enum/switch/`_isSlowDriver`/`_isLatinOnlyDriver`），设计债 |
| 并发 | 默认 8 并发，`--concurrency` 1~64 | 我们现在 `Future.wait` 无上限，源多了会同时打 |
| 超时 | `--timeout` 15s **覆盖该源的所有分页**；另有 `--deadline` 管总时长 | 我们缺"总 deadline"这一层，只有轮预算 |
| 去重 | **BTIH infohash** 去重 + tracker 合并 | 我们已有（`byHash`），OK |
| 排序 | seeders 降序，**未知排最后** | 我们把 0 当已知，死种和未知混在一起 |
| 过滤 | `matches_query` **中心化**放在 search_with_options：normalize 之后、dedup 之前 | 我们在 `_finalizeResults` 里，但只有子串包含，且不在源内先砍 |
| 可观测 | 每个源被丢弃的条数打到 stderr | 我们只有 `debugPrint` 失败，没有"丢了多少条" |

**最有价值的一条经验（v0.2.0 的 commit message 原文）**：

> "Measured against the live sources, **Knaben, Bitsearch, Nyaa and Sukebei all pad a query they cannot match with their most popular rows**: a default aggregate search for 子子西 returned 100 rows of which **none matched**. It now returns 12 rows and all 12 match."

我用这个结论复验了我们的场景：手机/PC 搜「战狼」，Knaben 返回 10 条里前 3 条是《EdMosaic 成人片》《牙狼》《金刚狼3》，只有第 3 条才是《战狼.2.Wolf.Warriors.2.2017》——**和它说的一模一样**。所以相关性过滤不是可选项，是接入这类聚合源的前提条件。

另外它保留了逃生口 `--no-title-filter`，因为子串过滤会误杀"拼写不同"的查询 —— 对我们就是**中文查询 vs 英文发布名**这个高频场景。

### 1.2 torrent-search-mcp（Python）

- `asyncio.gather` 并行 10 个源
- `SourceParser` protocol：把 JSON / RSS / HTML 三种格式**统一成同一契约**再往上抛
- `aiocache` 做结果缓存
- `EXCLUDE_SOURCES`（逗号分隔域名）可运行时排除源
- `INCLUDE_LINKS` 默认 false —— 只省传输，不改变架构

值得抄的是 **SourceParser 契约**：上层调度完全不关心源是 JSON 还是 HTML。

### 1.3 bitmagnet（Go，自建索引器）

- DHT 爬虫直接遍历 infohash → 拉 metadata → 内容分类器打标签（类型/语言/分辨率/来源）→ GraphQL 查询
- 不依赖任何索引站，自包含
- 代价：要一台常驻服务器 + 存储 + 带宽，alpha 状态，API/schema 会变

**结论：这条路不是我们现在该走的**（我们是纯客户端 App，没有服务端）。但如果将来做云端，这是唯一能彻底摆脱"第三方源随时挂"的方案。

### 1.4 Magnet Search（内嵌 Jackett）

- 源并行查询；"Search more sources"跑剩下的
- **`Source issues → Retry failed`：只重查失败的那几个源**，不是整轮重来
- 先打 general-purpose tracker 批次，再打其余

"只重试失败源"是个很实用的设计，我们现在是整轮重来。

## 2. 我们现在的实现与问题

### 2.1 现状

`lib/config/magnet_source_catalog.dart` 内置 6 个源，默认只开 2 个：

| 源 | driver | enabled | 说明 |
|---|---|---|---|
| Torrentio | torrentioJson | ✅ | **IMDb id 索引**，唯一稳定出结果的源 |
| apibay (TPB) | apibay | ✅ | **仅英文查询**，中文会返回热门榜垃圾 |
| YTS / 1337x / BT4G / Nyaa | — | ❌ | 真机实测全部连接超时 |

调度：`TorrentSearchService.searchPreferringImdb`
1. 片名 → IMDb id（豆瓣/TMDB/IMDb 联想）
2. **IMDb 轮**：只用 torrentio + yts
3. 空 → **回退标题轮**：用片名查所有源（串行！）

### 2.2 六个具体问题（按影响排序）

**① 单点依赖 —— 这是"波动"的根因**
能出结果的只有 Torrentio。它抖一次，整个磁力模块就空。
实测同一 URL：手机 2.43s / 60948B；PC 5.09s；此前还出现过 60s/3238B 与 6.66s/35736B 的巨大差异（服务端实时聚合多个 provider）。

**② 时间预算层层倒挂**
```
Dio receive        34s  （_slowDio）
单源硬超时          35s  （_slowSourceTimeout）
轮预算             34s  （_roundBudget）
调用方兜底          45s  （detail_torrent.dart / search_page.dart）
```
单源最坏 34s 就已经吃掉整个轮预算；两轮必然撞 45s，结果被 `TimeoutException` **整轮丢弃**——用户看到的是"磁力模块直接没了"，不是"搜得慢"。

**③ 完全没有缓存**
`CacheService` 是视频下载缓存，跟搜索结果无关。同一个片反复进详情页 = 每次都重新打 Torrentio（而它是服务端实时聚合，最慢的那种）。
magnet-cli 有 `cache.rs`，torrent-search-mcp 有 aiocache，我们这里是 0。

**④ 源内串行重试放大延迟**
`_searchTorrentioAt` 串行试 `movie/` → `series/`，每个候选都能吃满 34s。注释里写的原因是"并行会让对端双双超时"——这说明真实瓶颈在**我们等太久了**，而不是并发本身。

**⑤ 相关性过滤位置偏晚、规则单一**
只在 `_finalizeResults` 里用子串包含判断。对 `apibay` 中文查询有专门的 `_isLatinOnlyDriver` 拦截（好），但对**支持中文的聚合源**没有任何防护——接进来就会把《牙狼》《金刚狼》当《战狼》。

**⑥ IMDb 轮与标题轮串行**
解析错（战狼→Logan）时，IMDb 轮拿到的是错的片的全套资源，`_areResultsRelevant` 靠子串碰运气；碰不上才退回标题轮，又等一整轮。

## 3. 实测：候选新源评估

### 3.1 Knaben（强烈推荐）

`POST https://api.knaben.org/v1`，JSON body。**聚合器**（一次覆盖 TPB / YTS / 1337x / Nyaa 等 20+ 站）。

真机实测（手机 curl，非 PC 代理）：

| 请求 | 结果 |
|---|---|
| inception, size=5 | `code=200 total=3.64s size=8817` |
| Torrentio 同片对照 | `code=200 total=2.43s size=60948` |

PC 侧稳定性（连续 4 次，size=20）：**3.25s / 4.51s / 14.38s / 4.71s** —— 抖动同样明显，所以它是"多一个源"，不是"替代 Torrentio"。

返回字段（完整）：

```
hash / magnetUrl        → 可直接建 TorrentInfo
liveSeeders / livePeers → 实时做种/连接数（比 Torrentio 标题正则解析的静态值可靠）
seeders / peers         → 索引侧统计
bytes / title / category / categoryId
cachedOrigin / tracker / trackerId  → 来源站（可展示"来自 YTS/TPB"）
virusDetection          → 0~1 风险分，可做过滤
details                 → 原站详情页
```

**三条决定性验证**：

| 验证 | 结果 |
|---|---|
| 中文原名直查「我不是药神」 | ✅ `我不是药神 Dying To Survive (2018) 1080p WoBuShiYaoShen` 2.41GB —— **完全不经过 IMDb** |
| 中文「战狼」 | ⚠️ total=10，但前 3 条是牙狼/金刚狼/成人片 —— 必须配相关性过滤 |
| `tt1375666` 直查 | ❌ total=0 —— **它不支持 IMDb id，只能按标题** |
| size=100 | ✅ 返回 100 条，total 446，其中 **62 条 liveSeeders > 0** |

第一条是全局性的：**「战狼→Logan」这类错配，只要走原名直查路径就天然不会发生**。这比继续修 IMDb 打分更根本。

### 3.2 其他候选（实测排除）

| 源 | 实测 | 结论 |
|---|---|---|
| Comet (Stremio addon) `comet.elfhosted.com` | `403` / 9B | 需自建或配 debrid，公共实例不可用 |
| MediaFusion `mediafusion.elfhosted.com` | `200` 但 14B（空 streams） | 公共实例无结果 |
| Bitsearch API | `code=000` 10s 超时 | 真机大概率也不可达，不启用 |
| SolidTorrents API | `code=000` 10s 超时 | 同上 |
| bitmagnet | 需自建 Go 服务 | 与纯客户端定位冲突，P2 再看 |

### 3.3 分类参数（实测有效）

```json
{"query":"战狼","hide_unsafe":true,"categories":[2000000,3000000]}
```
加 `categories` 后成人内容被过滤掉（8 条全是影视/动漫）。
注意：`hideUnsafe`（驼峰）**无效**，必须 `hide_unsafe`（下划线），且它单独用不足以过滤，必须配 `categories`。

## 4. 优化方案

### P0 —— 小改动大收益（建议先做这三件）

#### P0-1 新增 Knaben 源

- `MagnetSourceDriver` 加 `knabenJson`
- `MagnetSourceCatalog.builtInDefaults` 加一条，`enabled: true`
- `_searchWithConfig` 加 case：Knaben 是 **POST**，不走 `buildUrl` 模板，单独构造 body
- 新方法 `_searchKnabenAt(String query, String label, int page)`
- body 固定：`search_type=100%`、`search_field=title`、`order_by=seeders`、`hide_unsafe=true`、`categories=[2000000,3000000]`、`size=50~100`
- 映射：`liveSeeders ?? seeders` → `TorrentInfo.seeders`；`hash` 拼 magnet（`magnetUrl` 为空时）；`cachedOrigin` 写进 `source`（展示"来自 TPB"）
- `_isLatinOnlyDriver` 返回 **false**（它支持中文）
- `_isSlowDriver` 返回 false，但给 12s（实测尾部能到 14s）

预期：可用源从 1.5 变 2，**中文片名首次有直接来源**，且不依赖 IMDb 解析。

#### P0-2 时间预算重排（消除倒挂）

建议新的一层结构：

| 层 | 建议值 | 说明 |
|---|---|---|
| 单源超时（快源） | 8s | Knaben/apibay |
| 单源超时（慢源） | 14s | Torrentio / Jackett |
| 单源内部最多候选 | 1 次请求 | `movie/` 为空才试 `series/`，**共享同一个 14s 预算**（现在各吃一份） |
| 单轮上限 | 20s | |
| 两轮上限 | 40s | |
| 调用方兜底 | 45s | 不动 |

关键：`_slowDio` 的 `receiveTimeout` 必须 **小于** 单源硬超时，否则 Dio 永远不会先报错、外层超时才是第一个触发的——现在是 34s vs 35s，几乎同时，日志里根本区分不出"是网络慢还是超时掐的"。

#### P0-3 搜索结果缓存（TTL 10 分钟）

- 新增轻量 `TorrentSearchCache`：内存 `Map<String, _Entry>`，上限 ~100 条，LRU 淘汰
- key = `归一化标题|年份|strict`（**不要**把磁力源配置拼进 key，否则用户开关源就全失效）
- 命中：**立即返回旧结果 + 后台刷新**（stale-while-revalidate）；后台失败不改 UI
- 失效：用户点「重新搜索」时跳过缓存
- 不落盘（磁力结果时效性强，几百 KB 也没必要写文件）

预期：从详情页退回再进去，**0ms 出结果**，不再打 Torrentio。

### P1 —— 结构性改进

#### P1-4 先到先交付 + 分阶段上报

现在的 `Future.wait` 语义是"等最慢的"。改成：
- 每个源完成即回调一批（复用 `searchFromAllSources` 已有的流式事件模型）
- UI 第一批结果先上屏，后续批次补齐
- 参考 magnet-cli 的 `concurrency` + `deadline`；参考 Magnet Search 的「只重试失败源」

#### P1-5 IMDb 轮与原名轮并行（不是串行 fallback）

```
现在：解析 IMDb → 查 IMDb 轮 → 空 → 查标题轮     （最坏 2×）
改为：解析 IMDb ─┬→ IMDb 轮 ──┐
                └→ 原名轮 ───┴→ 按 btih 合并，imdbId 匹配的优先
```

- 原名轮用原始片名（中文就是中文），走 Knaben
- 即使 IMDb 解析错（战狼→Logan），原名轮也能把正确的《战狼》捞回来
- 合并规则：btih 去重；同一 btih 上 `imdbId == 解析结果` 的条目优先
- 预算不叠加（两轮并行，总时长 ≈ 单轮）

#### P1-6 中心化相关性过滤（学 magnet-cli 的位置和规则）

位置：**normalize 之后、dedup 之前**，对每个源单独统计丢弃数。

规则（保留现有 `isSearchResultRelevant` 作为底层）：
- CJK 查询：标题必须含 CJK 子串，**或**含已知英文别名（`refineAlias` / resolved 英文名）
- 拉丁查询：子串命中，或切词命中过半
- **逃生口**：源内丢弃后该源结果 < 2 条时，放行（否则一刀切会把真结果杀光）
- 日志：`磁力源 Knaben 丢弃 8/10 条（含中文查询不匹配）`

#### P1-7 做种数语义统一

- `TorrentInfo.seeders` 用 **-1 表示未知**
- 排序：已知降序 → 未知排最后（magnet-cli 的做法）
- UI：未知显示「做种 ?」，不要显示「做种 0」（现在 Torrentio 解析失败就是 0，用户以为是死种）

## 6. 风险

| 风险 | 应对 |
|---|---|
| Knaben 是第三方公共服务，可能限流/下线 | 源配置里可开关；失败静默降级，不阻断其它源；`Search more sources` 手动重试失败源 |
| 中文相关性过滤误杀 | 保留逃生口（源内剩余 <2 条时放行）+「扩大范围/全站搜索」入口 |
| categories 参数可能随上游变更 | 解析时对 `category` 字符串二次过滤（`XXX` 前缀直接丢），不单靠请求参数 |
| Knaben 抖动（实测 3.2~14.4s） | 不设它为唯一源；单源 12s 超时；先到先交付 |
| 缓存导致片源更新看不到 | TTL 10min + 手动「重新搜索」绕过 |

## 7. 验证方式（方案落地后）

1. **单元测试**：Knaben 响应解析（真实 JSON 固件）、相关性过滤（战狼/我不是药神/Inception）、排序（已知 vs 未知做种）、缓存命中与 TTL
2. **真机对比**：同一批片（我不是药神 / 战狼 / Inception / 流浪地球）在 4G、WiFi 下各跑 5 次，记录「首次出结果时间 / 结果条数 / 可播条数」
3. **负向验证**：把 Knaben 源关掉，确认「战狼」重新出现金刚狼 —— 证明新增源确实在起作用

## 8. 建议的落地顺序

1. P0-1 加 Knaben（独立可验证，先能出中文结果）
2. P0-2 重排预算（之后再谈抖动才有意义）
3. P0-3 缓存
4. P1-5 双路并行（解决错配兜底）
5. P1-6 相关性过滤（Knaben 接进来后必须紧随，否则会放垃圾进列表）
6. P1-4 / P1-7

> 注：P0-1 和 P1-6 最好同一批上，因为 Knaben 不带过滤就会把《牙狼》当《战狼》塞进列表。
